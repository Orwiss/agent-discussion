# 멀티 에이전트 디자인 회의 시스템 — 구조와 흐름

## 전체 그림

```
사용자(Orwiss)
    │
    ▼
┌─────────────────────────────┐
│  Stage 1: 사전 정제          │  Facilitator와 1:1 대화
│  "오늘 뭘 논의할 건가요?"     │  → 회의 브리프 생성
└─────────────┬───────────────┘
              │ 브리프 (자동 전달)
              ▼
┌─────────────────────────────┐
│  Stage 2: 디자인 회의        │  회의 유형에 따라 구조가 달라짐
│  Round 1 → Round 2 → ...   │
└─────────────────────────────┘
```

---

## Stage 1: 사전 정제

Facilitator 에이전트와 Orwiss가 1:1로 대화한다.

**Facilitator가 파악하는 것:**
- 디자인 목표 (뭘 달성하려는가)
- 현재 상태 (있으면 설명, 없으면 백지)
- 제약 조건 (기술적, 시간적, 리소스)
- 피드백 범위 (뭘 논의하고 뭘 안 할 건지)

**Facilitator가 판단하는 것:**
- 회의 유형 자동 분류

| 유형 | 판단 기준 | 예시 |
|------|----------|------|
| 발산형 | 아직 구체적 디자인 없음, 방향 탐색 필요 | "몬스터 사냥 시스템을 어떻게 만들지?" |
| 개선형 | 기존 디자인 있음, 더 나아지길 원함 | "이 인벤토리 UI가 별로인데 어떻게 고치지?" |
| 선택형 | 후보 2~3개 있음, 골라야 함 | "A안과 B안 중 뭐가 나아?" |

**끝나면:**
회의 브리프를 출력한다. 이 브리프가 Stage 2의 시작점이 된다.

## Stage 2: 디자인 회의

### 참여자

| 에이전트 | 역할 | 추론 방식 | Groq 모델 |
|----------|------|----------|-----------|
| Orwiss | 사용자, 최종 판단 | 자유 개입 | — |
| UX 리서처 | 사용자 경험 관점 | 사용자 행동 시나리오를 3단계로 써서 막히는 지점 찾기 | `llama-3.3-70b-versatile` |
| 3D 디자이너 | 시각/공간 관점 | 다른 게임/앱/영화의 구체적 레퍼런스를 대고 변형 제안 | `mixtral-8x7b-32768` |
| 언리얼 개발자 | 기술 실현 관점 | 기술 스펙과 공수를 나열하고 "안 되지만 대신 이건 된다" 대안 제시 | `llama-3.3-70b-versatile` (내부 검토 에이전트 하나가 `gemma2-9b-it`) |
| Synthesizer | 정리자 | 아이디어 보드 관리 (tool 함수로 직접 수정), 라운드 마무리 | `llama-3.3-70b-versatile` |

**모델을 일부러 다르게 배정하는 이유:**
같은 모델이면 같은 키워드 어트랙터를 공유한다. "UE5 하면 떠오르는 것" 목록이 동일해서 에이전트마다 같은 말만 반복하게 됨.
- llama, mixtral, gemma는 학습 데이터와 아키텍처가 다름 → 같은 주제를 줘도 다른 키워드를 먼저 떠올림
- 이게 프롬프트 수정보다 근본적인 반복 방지책
- 언리얼 개발자 본체는 llama-70b (gemma2는 8K 컨텍스트 제한이라 대화 길어지면 터짐), 대신 내부 검토 에이전트 하나를 gemma2로 배정해서 이질성 유지

### 핵심: 각 에이전트는 SocietyOfMind로 구현 (내부 검토)

UX 리서처가 발언할 때, 바로 말하는 게 아니라 **머릿속에서 여러 각도로 생각한 다음** 정제된 한마디를 내놓는다. 그 "머릿속 생각 과정"을 AG2가 실제로 구현해주는 것:

```
[본 회의에서 UX 리서처 차례]
    │
    ▼ (내부 검토 — 본 회의에는 안 보임)
┌──────────────────────────────────────────────┐
│  UX 내부 검토                                 │
│  시나리오 분석가: "사용자가..."                 │
│  접근성 검토자: "근데 이건..."                  │
│  탈선 유도자: "그건 저번에 이미 나온 이야기고,  │
│               아직 안 나온 건..."              │
│  → 정제된 하나의 의견 도출                     │
└──────────────────────────────────────────────┘
    │
    ▼
[본 회의에 발언: 정제된 의견]
```

이렇게 하면:
- 본 회의는 3~4명이 깔끔하게 진행
- 하지만 실제로는 9명 이상의 관점 반영
- 발언 하나하나의 밀도가 높음
- 내부 검토 내용은 본 회의 토큰에 안 쌓임

**탈선 유도자의 역할 (반복 방지 핵심):**
각 에이전트의 내부 검토 마지막에 "탈선 유도자"가 있다. 이 에이전트의 역할은:
- "본 회의에서 이미 나온 키워드/주제 목록"을 받아서
- "그건 이미 나왔으니, 아직 안 나온 관점을 찾아라"고 강제

이러면 내부 검토 단계에서 이미 중복이 걸러지고, 본 회의 발언이 매번 달라진다.

---

### 반복 방지 — 3중 안전장치

이전 시스템에서 에이전트가 같은 키워드에 갇혀 반복하는 문제가 있었다 (UX는 매번 동적 효과, 개발자는 매번 LOD/셰이더). 이를 3중으로 방지:

**1단계: 모델 이질성 (근본 원인 차단)**
에이전트마다 다른 LLM 모델을 사용해서, 같은 주제를 줘도 다른 연상 패턴이 나오게 함.

**2단계: 내부 검토 탈선 유도자 (발언 생성 시점에서 차단)**
각 에이전트의 내부 검토에서 "이미 나온 것 말고 다른 걸 찾아라"를 강제.

**3단계: 키워드 추적 + 금지어 동적 주입 (시스템 메시지 레벨)**
에이전트별로 이미 사용한 핵심 키워드를 추적하고, 매 턴 시스템 메시지에 주입:

```
당신이 이전에 이미 언급한 주제: [동적 효과, 마이크로인터랙션, 온보딩 플로우]
이번 발언에서는 이 주제를 반복하지 마세요. 완전히 다른 각도에서 접근하세요.
```

고정 프롬프트가 아니라 **매 턴 변하는 동적 금지 목록**이라, 대화가 진행될수록 새로운 방향으로 밀어줌.

### 회의 유형별 흐름

#### 발산형: 발산-수렴 사이클

```
Round 1 (넓게 탐색)
├── 자유 발언, speaker selection이 "아직 안 나온 관점"을 가진 사람 우선 지명
├── 아이디어 보드에 계속 추가됨
└── 수렴: "발전 가능성 큰 아이디어 2개 + 미탐색 방향 1개" 자동 추출
         │
         ▼
Round 2 (좁혀서 깊이)
├── Round 1에서 고른 아이디어를 발전시킴
├── 새 방향도 탐색
└── 수렴: 같은 방식으로 다시 추출
         │
         ▼
Round 3 (마무리)
├── 가장 유망한 방향을 구체화
└── 최종 정리: 선택지 + 각각 얻는 것/잃는 것 + 미해결 이슈
```

#### 개선형: 문제 → 해결

```
Round 1 (문제 발견)
├── 각자 현재 디자인의 문제점 식별
├── 해결책 아직 안 냄
└── 수렴: 문제 목록 정리, 우선순위
         │
         ▼
Round 2 (해결책 탐색)
├── 합의된 문제에 대해 각자 해결책 제안
├── "만약 ~라면?" 형식
└── 수렴: 해결책 후보 정리
         │
         ▼
Round 3 (구체화)
├── 유망한 해결책 발전
└── 최종 정리
```

#### 선택형: 후보별 탐색

```
Round 1 (각 후보 탐색)
├── 후보 A에 대해 각 관점에서 평가
├── 후보 B에 대해 각 관점에서 평가
└── 수렴: 후보별 장단점 정리
         │
         ▼
Round 2 (비교 + 하이브리드)
├── 직접 비교, 새 조합 가능성
└── 최종 정리: 추천 + 근거
```

### 공유 아이디어 보드

모든 에이전트가 항상 볼 수 있는 공유 상태:

```
현재 아이디어 보드:
─────────────────
1. [UX] 인벤토리를 방사형으로 배치 → 접근성 좋지만 확장 어려움
   └── [3D] 방사형인데 깊이감으로 카테고리 구분하면?
2. [Unreal] 물리 기반 드래그앤드롭 → 재미 있지만 모바일 이식 불가
3. [미탐색] 소리/촉각 피드백 방향은 아직 안 나옴
```

- 매 턴마다 에이전트 시스템 메시지에 주입됨
- 이미 나온 아이디어와 겹치지 않는 방향을 찾게 유도
- Synthesizer가 AG2 내장 tool(함수 호출) 기능으로 보드를 직접 수정

---

### 발언 순서 결정

단순 round robin이 아니라, "아이디어 기여도" 기반:

> "지금까지 나온 아이디어 중 아직 충분히 발전되지 않은 것이 있다면,
> 그걸 가장 잘 발전시킬 수 있는 사람을 골라라.
> 모든 아이디어가 충분히 탐색되었다면,
> 가장 다른 관점을 가진 사람을 골라라."

이러면 한 사람이 연속으로 말할 수도 있고, 필요한 사람이 자연스럽게 호출됨.

---

### 발언 품질 가드레일

에이전트가 발언하기 직전에 자동 체크 (최후의 안전망):
- 이전 발언과 실질적으로 같은 내용인가? → 다른 각도를 찾아서 다시
- 구체적 근거(시나리오/레퍼런스/기술스펙)가 없는가? → 추가하고 다시

반론 강제가 아니라 **새로움 강제**. 디자인 회의에 맞는 가드레일.

---

### Orwiss의 개입

모든 라운드에서 Orwiss가 선택된 시점에 인풋을 받음:
- 텍스트 입력 → 그게 발언이 됨
- Enter → 넘어감 (AI끼리 계속)
- "exit" → 회의 종료

언제든 방향을 틀거나, 특정 아이디어를 더 파보라고 지시 가능.

```
agent-discussion/
├── .env                   # Groq API 키 (사용자가 직접 입력)
├── config.py              # Groq LLM 설정, 모델 배정
├── agents/
│   ├── facilitator.py     # Stage 1 Facilitator
│   ├── ux_researcher.py   # UX 리서처 (SocietyOfMind — 내부 검토)
│   ├── designer_3d.py     # 3D 디자이너 (SocietyOfMind — 내부 검토)
│   ├── unreal_dev.py      # 언리얼 개발자 (SocietyOfMind — 내부 검토)
│   └── synthesizer.py     # Synthesizer
├── meeting/
│   ├── stage1.py          # 사전 정제 로직
│   ├── stage2.py          # 디자인 회의 로직
│   ├── idea_board.py      # 공유 아이디어 보드 관리
│   ├── speaker.py         # 커스텀 speaker selection
│   └── guardrails.py      # 반복 방지 가드레일
├── prompts/
│   ├── facilitator.py     # Facilitator 시스템 프롬프트
│   ├── ux_inner.py        # UX 내부 검토 에이전트 프롬프트들
│   ├── designer_inner.py  # 3D 내부 검토 에이전트 프롬프트들
│   ├── unreal_inner.py    # Unreal 내부 검토 에이전트 프롬프트들
│   └── synthesizer.py     # Synthesizer 시스템 프롬프트
└── main.py                # 진입점
```
